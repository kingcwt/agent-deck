# Git Diff Review

## Description

读取当前仓库改动，并输出简洁中文审查：说明每个文件改了什么、实现是否还能更小、是否可能影响其他模块或逻辑。

## Parameters

- 必填：无。
- 可选语言：默认中文；只有用户明确要求英文时才输出英文。
- 输出：逐文件改动说明，加审查结论、最小化实现建议和影响范围说明。

## Shortcuts And Commands

- Codex 快捷键：`$kc-gdd`
- Codex 完整命令：`$kc-gdd`
- Claude Code 快捷键：`/kc-gdd`
- Claude Code 完整命令：`/kc-gdd`

## Examples

### Codex

```text
$kc-gdd
```

### Claude Code

```text
/kc-gdd
```

## Workflow

### 1. 先找出所有改动文件

- 把 `/kc-gdd` 和 `$kc-gdd` 视为这个工作流的显式快捷触发词。
- 把这次触发本身当作本轮唯一任务，不要继续上一段对话话题，也不要拿它去回答上一个非命令问题。
- 从当前仓库状态开始，在写任何描述之前先识别出所有改动文件。
- 包含 staged 和 unstaged 的已跟踪改动，也包含当前工作区里的 untracked 文件。
- 保持文件级粒度，主要输出单位是“每个改动文件一条描述”。
- 如果没有任何改动文件，就直接说明并停止。

### 2. 结合足够上下文阅读 diff

- 对每个改动文件，先检查它自己的 git diff。
- 如果仅看 diff 还不足以判断改动内容，就继续阅读该文件当前内容。
- 只补充理解这个改动所必需的最近邻代码或引用，例如相关组件、类型、工具函数或调用点。
- 对于 untracked 文件，直接读取文件内容，并结合文件名和内容推断它的用途。
- 对于被删除的文件，结合删除 diff 和周边引用说明删掉了什么。

### 3. 用中文逐文件说明改动

- 默认输出语言是中文。除非用户明确要求英文，否则不要输出英文。
- 每个改动文件输出一条简短主描述。
- 每条描述都要短、具体、以动作表达为主。
- 优先使用类似 `新增登录按钮`、`补充 UserSession 类型`、`调整订单列表请求参数`、`删除废弃支付回调` 这样的表述。
- 要点名真正变动的功能、类型、字段、组件、配置或行为，避免 `优化代码`、`修复一些问题`、`更新逻辑` 这类空泛说法。
- 如果一个文件里有多个彼此强相关的改动，要压缩成一句能表达主意图的短句。
- 如果无法完全确定真实意图，要基于代码谨慎表述，例如写成“看起来是”“大概率用于”“用于补充”。

### 4. 审查改动文件

- 逐文件说明之后，继续审查 diff 里是否有需要修的问题。
- 检查每处改动是否符合当前需求下的最小安全实现。
- 标记冗余代码、重复逻辑、不必要抽象、猜测式配置、过宽重写或无关清理。
- 检查是否应该复用已有工具函数、组件、类型、API 结构或本地模式，而不是新增逻辑。
- 检查是否影响共享模块、共享组件、公共类型、配置、数据库相关代码或跨页面行为。
- 如果某个改动可能影响其他模块或调用方，点名受影响的模块或调用路径。
- 如果没有需要修的问题，写 `未发现需要修改的问题。`
- 审查意见保持简洁、可执行，不要展开成长教程。

### 5. 保持输出紧凑

- 默认使用以下输出结构：
  - `改动文件`：扁平列表，形如 `path: 中文简短描述`。
  - `审查结论`：按严重程度列出发现，或写 `未发现需要修改的问题。`
  - `影响范围`：说明跨模块或行为影响，或写 `未发现明显跨模块影响。`
- 整体回答要尽量短，让用户能快速扫完整个改动集。
- 当用户要求逐文件描述时，不要把多个文件压缩成一个整仓库总述。

## Guardrails

- 这是一个“简洁改动审查”工作流，不是代码修改或提交代码的工作流。
- 默认只读审查。除非用户明确要求修复，否则不要修改代码。
- 默认必须输出中文。只有用户明确要求英文时才允许输出英文。
- 只要 diff 或文件内容可读，就不要只凭文件名编造描述。
- 代码里有明确业务名词或技术名词时，不要退化成泛化标签。
- 除非用户明确缩小范围，否则不要静默跳过改动文件。
- 如果无法高置信判断文件用途，要简短说明不确定性，不要把推断说成确定事实。
